# EFIMS Frontend

Next.js (App Router) + TypeScript + Tailwind CSS v4 + shadcn/ui, per `../CLAUDE.md`'s confirmed
toolset. Talks to the `efims-backend` REST API — and only from the server side of this app; see
"Security architecture" below for why the browser never calls the backend directly at all.

**Built so far:** the auth/session architecture (login, logout, route protection, silent token
refresh), the dashboard shell (sidenav/topnav), and — following the same pattern `incidents`
established as the first vertical slice — full frontend coverage of every backend module:
`signals` (queue, intake form, validate/reject), `incidents` (list + detail: triage assessment/
escalation, SLA clock start/pause/resume/stop, relate/merge), `cases` (list, create, and a
tabbed detail view — Overview, Approvals, Investigations, Evidence, Containment, Recovery, CAPA,
Regulatory), `workflow` (the approval-request/approve/reject flow, surfaced inside the Approvals
tab), `audit` (read-only trail), `configuration` (CD-01..CD-08 list + detail), and `notifications`.
Every page is a real Server Component reading from the live backend, every write is a real Server
Action — nothing here is a static mock.

## Stack notes

- **Next.js 16**, not 15 — a materially different version from what most training data and
  tutorials describe. `middleware.ts` is deprecated in favor of `proxy.ts` (renamed function too:
  `export function proxy(...)`, not `middleware`); `cookies()`/`headers()`/`params`/
  `searchParams` are now fully async everywhere, no synchronous compatibility shim left; Turbopack
  is the default bundler for both `dev` and `build`. Before touching a Next.js API this project
  hasn't used yet, check `node_modules/next/dist/docs/` — bundled, version-matched docs — rather
  than trusting prior familiarity with an older version. `AGENTS.md` at this project's root exists
  for exactly this reason (auto-regenerated by `next dev`; keep it, don't delete it).
- **Tailwind v4** — CSS-first config (`@theme` blocks in `globals.css`), not a `tailwind.config.js`
  file. The mockups (Tailwind v3, CDN, JS config objects) needed translating, not copying.
- **shadcn/ui**, initialized via `npx shadcn@latest init`. Its own default (grayscale, oklch)
  theme was fully replaced with the Botanical Executive tokens — see "Design system" below.

## Security architecture

**The browser never talks to the EFIMS backend at all** — every backend call happens from this
Next.js server (Server Components for reads, Server Actions for writes), never from a Client
Component. `BACKEND_URL` (`src/lib/env.ts`) has no `NEXT_PUBLIC_` prefix and `src/lib/
backend-client.ts` imports `server-only`, so it's a build error, not just a convention, for that
origin to ever reach a client bundle. This is a step further than the confirmed toolset's own rule
("talks to backend only via REST, no direct DB access") — here, not even the API origin itself is
exposed to client JS.

**Session**: the backend's own signed JWTs (`accessToken`, `refreshToken` from `POST /auth/login`)
are stored verbatim in two `HttpOnly`, `SameSite=Lax` cookies (`src/features/auth/session.ts`) —
deliberately NOT re-wrapped in a second app-level encrypted session token. The backend already
issues short-lived (15m), signed access tokens and rotating refresh tokens with reuse detection;
wrapping them again would add complexity without adding security, since these cookies are already
unreachable from client JS (the actual XSS-theft mitigation) and the JWTs are already
tamper-evident by their own signature. `decodeJwtPayload` reads claims for optimistic UI only —
role badge, nav gating — never as an authorization decision.

**Two layers of auth check, matching the Next.js authentication guide's own recommendation**:

1. `src/proxy.ts` — optimistic, cookie-only redirect gate (Next 16 renamed `middleware.ts`). Runs
   on every navigation, decodes (never verifies) the access-token cookie, and redirects toward or
   away from `/login`. Deliberately self-contained (no imports from `src/features/`/`src/lib/`,
   duplicating its own tiny JWT-decode function) — per Next.js's own Proxy docs: "Proxy is meant
   to be invoked separately of your render code... you should not attempt relying on shared
   modules or globals." Also does silent access-token refresh: since Server Components can only
   *read* cookies (writing one during render throws), and Proxy is the one place that runs before
   every navigation *and* can set cookies on the response, this is what keeps a Server Component
   from ever having to handle a live-expired token mid-render.
2. `requireSession()`/`getSession()` (`src/features/auth/session.ts`) — the real DAL check, called
   in the `(app)` layout and in every page under it. A bug in Proxy's matcher can only ever produce
   a wrong *redirect*; it's this second check, and ultimately the backend's own re-verification of
   the token's signature/expiry/role/compartment on every real request, that's the actual
   authorization boundary. RLS, the 7-condition case-access rule, and every other backend
   enforcement mechanism apply exactly as they do to any other caller — this frontend adds no
   authorization logic of its own, on purpose.

**Login/logout are Server Actions** (`src/features/auth/actions.ts`, `'use server'`), not a
client-side `fetch` to a public API route — form data never leaves the server boundary before
being validated (zod) and forwarded to the backend.

## Design system

Tailwind theme tokens in `src/app/globals.css`'s `@theme` block are transcribed verbatim from
`../docs/design-system.md` v1.2.0's "Botanical Executive" palette (reconciled 2026-09-18 against
all 35 mockup screens) — exact hex values, not approximations. Material-3-style token names
(`primary`, `primary-container`, `on-secondary-container`, `surface-container-low`, ...) are
exposed directly as Tailwind utilities (`bg-primary-container`, `text-on-secondary-container`,
...) *and* mapped onto shadcn/ui's own semantic slots, so every shadcn primitive (`Button`,
`Card`, `Badge`, `Table`, ...) already renders in-palette with no per-usage override. Severity
tokens (`severity-s1`..`severity-s4`) are a deliberately separate raw-utility layer, matching the
source doc's own note that these are never derived from the brand tokens.

Fonts: Plus Jakarta Sans (body/UI, `next/font/google`), Playfair Display (headlines,
`next/font/google`), JetBrains Mono (`next/font/google` — the mockups load it but never actually
wire it into Tailwind's `mono` family, a gap this app closes rather than repeats), Material
Symbols Outlined (icon ligature font, loaded via a `<link>` in the root layout's own `<head>` —
correct for App Router, not a `_document.js`-era mistake; see the `eslint-disable` comment next to
it for why `no-page-custom-font` doesn't apply here).

`mockups/screens/*.html` were used as **layout and component reference**, not copied verbatim —
per `mockups/README.md`'s own instruction. Two deliberate departures from what the mockups show,
both because the real backend doesn't support what the mockup depicts:

- **No FIDO2/YubiKey/hardware-key MFA on the login screen** (`mockups/screens/login-mfa.html`).
  The real `identity` backend module is single-factor (tenant slug + email + password); building a
  second-factor UI with nothing behind it would be security theater, not a feature.
- **No fabricated KPI numbers** (`mockups/screens/command-center.html`'s static "42 Active
  Incidents" cards). Every number on the dashboard (`src/app/(app)/page.tsx`) comes from a real
  `GET /incidents` call's `total` field, filtered by real status — matching this whole project's
  standing rule to never present invented data as if it were live.

## Modular structure

Mirrors the backend's own module boundaries (`CLAUDE.md` non-negotiable #2, extended here even
though there's no enforced compile-time boundary the way NestJS modules give the backend):

- `src/features/<module>/` — one directory per backend module (`auth`, `signals`, `incidents`,
  `triage`, `workflow`, `cases`, `teams`, `users`, `investigations`, `evidence`, `containment`,
  `recovery`, `capa`, `regulatory`, `audit`, `notifications`, `configuration`). Each holds that
  module's `types.ts` (hand-kept in sync with the matching Prisma enums/DTOs — there's no shared
  package between the two apps; see the doc comment on `features/auth/types.ts` for why), its
  server-only `api.ts` (thin, typed wrappers around `backendFetch`), and (except `audit`, which is
  read-only from the outside per `CLAUDE.md` non-negotiable #3) an `actions.ts` (`'use server'`,
  each action pairing a `requireSession()` + api call + `revalidatePath(...)`). A page under
  `src/app/` should only import from the one feature module its route corresponds to, plus shared
  `components/`/`lib/`. `features/cases/get-case-cached.ts` wraps its case-lookup in React's
  `cache()` so the case detail layout and each of its 7 tab pages share one fetch per request
  instead of refetching the same case on every tab navigation.
- `src/lib/` — cross-module infrastructure: `env.ts` (server-only env accessors), `backend-client.ts`
  (the one place that knows the backend's origin), `utils.ts` (shadcn's own `cn()` helper).
- `src/components/ui/` — shadcn/ui primitives, unmodified except for the theme tokens.
- `src/components/shell/` — the dashboard chrome (`SideNav`, `TopNav`), used only by the `(app)`
  layout.

## Setup

1. `npm install`
2. Copy `.env.example` to `.env.local`. `BACKEND_URL` should point at a running `efims-backend`
   instance (default `http://localhost:3001`). Set `COOKIES_SECURE` to `"true"` once this app is
   served over HTTPS; leave `"false"` for plain-HTTP local dev only (browsers silently drop
   `Secure` cookies on plain HTTP, which would break login).
3. `npm run dev` — starts on `http://localhost:3000`. The backend must already be running and
   seeded (`efims-backend`'s own README) for login/incidents to have anything real to show.
4. Log in with the backend's seeded admin: tenant `bank-1`, `admin@bank1.efims.local`,
   `ChangeMe123!`.

## Real bugs this build found, not introduced

Building each module's pages and actually driving them in a browser (not just calling the API)
surfaced real bugs a purely API-level check would have missed:

- **CD-01 taxonomy data-quality bug** (found while building `incidents`): the "Whistleblowing"
  category had a `type` value of `"Whistleblower report (always WHISTLEBLOWING compartment,
  regardless of underlying subject matter)"` — CD-01's own explanatory note about how that category
  is *handled*, transcribed straight into the literal type-name string instead of staying a code
  comment. It sat there undetected through every prior backend-only live-testing pass (nothing
  ever rendered it as a user-facing label), but was immediately obvious as wrong the moment a real
  incidents table rendered it. Fixed in `efims-backend/prisma/seed.ts` and corrected directly in
  the already-seeded live rows via a one-off script against the privileged `DIRECT_URL`
  connection.
- **Blank dashboard page** (found while verifying the module expansion): `(app)/page.tsx` made two
  *sequential* (not parallel) uncached backend calls with zero loading UI. An ordinary Neon
  round-trip — or one of this project's well-documented transient latency spikes — meant the
  browser painted nothing at all until both resolved (measured live: 6.8s for `/`, 16.4s for
  `/login`). Fixed with `Promise.all(...)` for the two calls plus `(app)/loading.tsx` and
  `(app)/incidents/loading.tsx` (Skeleton-based) so the shell paints immediately regardless of
  fetch duration.
- **Signal-validate redirected to the wrong id** (found live during the module-expansion
  verification pass, not a hypothetical): the backend's `SignalsService.validate()` returns the
  *updated Signal* row, not an Incident — the newly created (or linked) incident's id lives on that
  row's own `incidentId` field, `.id` is still the signal's own id. `features/signals/api.ts`
  mistyped the response as `Incident`, and `features/signals/actions.ts` redirected to
  `/incidents/${incident.id}` — silently using the signal's id instead. Every incident reached this
  way 404'd, which cascaded into apparent failures for triage, the SLA clock, and case creation in
  end-to-end verification (they were never actually broken — the page they landed on just didn't
  exist). Fixed by correcting the return type to `Signal` and redirecting via
  `validated.incidentId`.
- **Missing shared error boundary** (found the same pass, after the bug above): before this fix,
  an uncaught `ApiError` (e.g. a 400 from bad taxonomy input) crashed the whole page with Next.js's
  raw dev error overlay instead of a graceful in-app message. Added `(app)/error.tsx` — a single
  Client Component boundary covering every Server Action/Component under `(app)/`, per Next.js's
  own `error.tsx` convention — rather than per-form inline validation, given how many Server-Action
  forms this app now has.

**Not a bug, confirmed by design**: verifying the case-detail "add a subject/conflict flag"
feature initially "failed" with `ApiError: Not authorized to access this case` on every subsequent
request. Root cause: the only seeded user is the admin driving the test, and flagging *that same
user* as a case `SUBJECT` correctly locked them out of their own case per `CLAUDE.md`
non-negotiable #6 ("user not a subject/conflict on the case"). Working as designed — the fix was
to the verification script, not the app: it now creates one disposable `INVESTIGATOR`-role test
user directly against the backend (there's no user-management UI in this frontend yet, so this
one setup step goes around the browser) purely so there's someone else to flag.

This is exactly the kind of thing "run it and look at the browser" catches that pure API-response
testing doesn't — see the project-wide instruction to actually verify UI changes in a browser
before calling them done.

## Live-verified

End to end against the real running backend, driven by a headless Chromium (Playwright) script,
not just a description of expected behavior. Two passes:

**Auth + dashboard + incidents (first slice)**:
- Visiting `/` while unauthenticated redirects to `/login` (Proxy's optimistic check).
- Submitting the login form with the seeded admin credentials sets the session cookies and
  redirects to `/`.
- The dashboard renders real KPI numbers (`Open incidents`/`Under review`, sourced from
  `GET /incidents?status=...`'s `total` field) and the sidenav/topnav shell (role badge, sign-out).
- The Incidents page renders real rows (`INC-2026-0001`/`INC-2026-0002`, correct compartment and
  status badges, correct category/type strings after the CD-01 fix above).
- Signing out redirects to `/login`, and visiting `/` again afterward redirects back to `/login`
  — confirming the session cookies were actually cleared server-side, not just hidden client-side.

**Full module expansion (every module above)**, one continuous flow through real data: log a new
signal → validate it into a new incident → initial triage assessment → start the SLA clock →
create a case linking that incident → add a subject/conflict flag → request a `CONTAINMENT`
approval → attempt (and correctly get rejected on) self-approval, confirming the
segregation-of-duties rule → save an investigation plan → ingest an evidence item → record a
recovery loss → CAPA and Regulatory tabs render → the Containment tab correctly shows its
"request one on the Approvals tab first" guard (no approved request exists yet) → the Audit Trail
renders real events → Configuration list/detail render real CD-01..CD-08 values → Notifications
renders real rows. All steps pass, **zero browser console errors**, screenshots reviewed for
design-token/layout correctness on the case-detail tabs (the most form-heavy pages).

## What's deliberately not here yet

- No real-time UI on the `notifications` page — the backend's Socket.IO gateway has no frontend
  client wired in yet; the page says so explicitly rather than silently looking finished.
- No user-management UI (`identity`'s `POST /users` exists on the backend; the frontend only reads
  `GET /users` for name-lookup dropdowns/flag pickers). Creating/editing users, teams, and
  compartment grants all still requires going straight at the backend.
- No client-side form validation library beyond the login form's own zod schema and each form's
  native HTML `required`/`minLength` — every Server Action validates via the backend's own
  class-validator DTOs and surfaces failures through the shared `(app)/error.tsx` boundary, not
  per-field inline state. A `useActionState`-based inline-error upgrade on the highest-traffic forms
  is a reasonable follow-up, not done here.
- Configuration is read-only in this frontend on purpose — CD-01..CD-08 are working defaults per
  `CLAUDE.md` non-negotiable #9, not something to let a UI make look formally ratified.
- No automated test suite (no Playwright config committed to this repo, no component tests) —
  verification so far is manual/live, matching the backend's own established practice at this
  stage of the build. The ad hoc Playwright scripts used to verify this session's work were run
  from a scratch location outside this repo, not committed here.
- `next.config.ts`'s `turbopack.root` pin is a local Windows-machine fix (an unrelated
  `package-lock.json` higher up this machine's user-profile directory tree was confusing Turbopack's
  root inference) — harmless elsewhere, but worth knowing why it's there if it ever needs revisiting
  on a different machine/CI setup.
